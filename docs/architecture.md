# ClinOps — Architecture

> Status: partially built. This document describes the full *intended*
> architecture; the ML pipeline (ETL → features → models → MLflow → BentoML
> serving) is implemented, while the orchestrators remain stubs. See the README
> Roadmap for per-stage status.

## Principle: one pipeline, many orchestrators

The core idea is an **orchestrator-agnostic pipeline**. The steps are defined
once as plain Python functions in
[`src/clinops/tasks/pipeline_tasks.py`](../src/clinops/tasks/pipeline_tasks.py):

```
extract → parse_fhir → build_features → train → evaluate → promote → package
```

Airflow, Prefect, and Kubeflow each **import and wrap** these functions. None of
them re-implement pipeline logic. That keeps the comparison honest: the only
thing that differs between orchestrators is the orchestration, not the work.

## Layers

| Layer | Module(s) | Responsibility |
|-------|-----------|----------------|
| Data source | Synthea (external) | Generate synthetic FHIR R4 bundles into `data/raw/`. |
| ETL | `etl/synthea_loader.py`, `etl/fhir_parser.py` | Load bundles, flatten FHIR resources into tables (`data/interim/`). |
| Features | `features/build_features.py` | Build the shared feature matrix + target (`data/processed/`). |
| Models | `models/sklearn_models.py`, `models/torch_model.py` | Baselines (LogReg, GBM) + PyTorch challenger on identical features. |
| Training | `training/train.py`, `training/evaluate.py` | Fit, log to MLflow, evaluate on a held-out split. |
| Registry | `registry/promote.py` | Champion/challenger promotion in the MLflow registry. |
| Serving | `serving/bentoml_service.py` | Package champion, serve REST `/predict`. |
| Core | `tasks/pipeline_tasks.py` | The orchestrator-agnostic step functions. |
| Orchestration | `orchestration/{airflow,prefect,kubeflow}/` | Thin wrappers over the core. |

## Infrastructure

The MLflow "spine" runs via Docker Compose ([`docker-compose.yml`](../docker-compose.yml)):

- **MLflow** — tracking server + model registry.
- **Postgres** — MLflow backend (metadata) store.
- **MinIO** — S3-compatible artifact store for models and run artifacts.

Airflow runs via its own compose file
([`orchestration/airflow/docker-compose.airflow.yml`](../orchestration/airflow/docker-compose.airflow.yml));
Kubeflow runs on a local `kind` cluster
([`orchestration/kubeflow/kind-config.yaml`](../orchestration/kubeflow/kind-config.yaml)).

## Data flow

1. Synthea → `data/raw/` (synthetic FHIR R4 bundles).
2. ETL → `data/interim/` (flattened clinical tables).
3. Features → `data/processed/` (feature store: shared X, y).
4. Training → MLflow runs (params, metrics, model artifacts).
5. Promotion → MLflow registry (champion selected).
6. Serving → BentoML loads champion, exposes `/predict`.

See [`orchestrator-comparison.md`](orchestrator-comparison.md) for the
Airflow vs. Prefect vs. Kubeflow trade-off write-up.

## Generating data

The cohort is built from **synthetic** patients generated by
[Synthea](https://github.com/synthetichealth/synthea) — there is **no real
patient data and no PHI**, ever. Generation is not committed; `data/` is
git-ignored.

```bash
make synthea       # generate ~1000 patients of FHIR R4 JSON into data/raw/
```

This requires **Java 11+**. The target downloads `synthea-with-dependencies.jar`
from the official GitHub release if it is not already present, then runs Synthea
with the FHIR exporter enabled (`--exporter.fhir.export=true`). Output lands in
`data/raw/fhir/`. Synthea also writes `hospitalInformation*` and
`practitionerInformation*` bundles (no `Patient` resource); the loader skips
these automatically and keeps only bundles containing a patient.

Override the population size or jar location via make variables, e.g.
`make synthea SYNTHEA_POP=200`.

## The readmission label (`readmission_30d`)

The prediction target is derived in
[`fhir_parser.label_readmission_30d`](../src/clinops/etl/fhir_parser.py). The
exact rule:

1. Take the patient's **inpatient** encounters (encounter `class.code` in
   `{IMP, ACUTE, NONAC}`, or a class display containing "inpatient").
2. Order them by **start** time. Encounters with no start time are ignored; an
   encounter with no end time falls back to its own start time.
3. The label is **`1`** if any inpatient encounter *starts* on or within
   **30 days** after the *end* of the immediately preceding inpatient encounter;
   otherwise **`0`**.

After parsing, the class balance (positive count and percentage) is logged. If
positives are zero or under 1%, a **WARNING** is logged that the label looks
degenerate and the derivation may need revisiting — we do **not** invent or
rebalance a label to make it look healthy.
